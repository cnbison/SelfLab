## 设计权衡

### 1. fake litellm 注入模式

为了在 litellm 不可用时也能测试 `real_*_identity` / `real_*_narrative` / `real_chat` 路径，需要绕过 litellm 的真实 import。设计：

```python
fake = ModuleType('litellm')
fake.__path__ = []  # 标记为 package
fake.completion = _FakeCompletions()
sys.modules['litellm'] = fake

# exceptions 子模块独立注入
fake_exc = ModuleType('litellm.exceptions')
for name in ['InternalServerError', 'APIConnectionError', ...]:
    setattr(fake_exc, name, type(name, (Exception,), {}))
sys.modules['litellm.exceptions'] = fake_exc

# 主模块也需要挂载异常类（适配 `litellm.InternalServerError` 访问）
for name, cls in exception_classes.items():
    setattr(fake, name, cls)
fake.exceptions = fake_exc
```

**关键细节**：`fake.__path__ = []` 是 module → package 的标志，缺它则 `import litellm.exceptions` 会抛 ModuleNotFoundError。**双重注入**（`sys.modules['litellm']` + `sys.modules['litellm.exceptions']`）是适配代码两种访问方式（`litellm.foo` vs `from litellm.exceptions import foo`）。

### 2. real_llm 测试 vs stub_llm fixture

第三批 4 模块大量需要测试 `real_*` 函数路径。但 `stub_llm` fixture 是 `MagicMock` + `side_effect` 模式（返回 deterministic `fake_chat_json` 值），无法覆盖以下关键场景：

- LLM 返回 None（需要 `chat_json.return_value = None`）
- LLM 返回非 dict 类型（如 string 描述）
- LLM 返回字段缺失 / 类型错误
- Validation 用 `self.llm.chat()`（非 `chat_json`），需要单独 `llm.chat.return_value`

**决策**：real_* 测试用 fresh `MagicMock()` 实例，自行控制每个属性。`stub_llm` fixture 仅供 orchestrator / TwinSession 集成测试使用（保持 fixture 的语义清晰）。

### 3. narrative.py 字符串返回处理

真实 LLM 调用 `real_build_narrative` 时，常见返回 3 种格式：

1. `{"narrative": "..."}` — 标准 JSON 对象（与 critic / identity 一致）
2. `"我是来自 X 的学生..."` — 直接返回字符串（真实 LLM 经常这样，简化输出）
3. `{"error": "..."}` — 错误响应

原代码 `parsed.get('narrative', str(parsed)[:500])` 在 case 2 时 `parsed` 是字符串，`.get` 抛 AttributeError。修复：

```python
if parsed is None:
    narrative = stub_build_narrative(crystallized_events, current_identity, seed=seed)
elif isinstance(parsed, str):
    narrative = parsed
else:
    narrative = parsed.get('narrative', str(parsed)[:500])
```

与 identity.py 的 `isinstance(parsed, str)` 处理模式对齐。**触发场景**：M2.2 v5/v6 实验中已观察到 Anthropic 兼容协议下模型倾向直接输出 narrative 文本。

### 4. session `__del__` warning 触发机制

测试 `__del__` 时遇到难点：`del session` 不触发 `__del__` 因为对象在 `_session_registry` 中仍有引用（registry 持有 strong ref）。解决方案：

```python
# 从 registry 移除（否则对象还有引用，__del__ 不会触发）
_session_registry.pop(sid, None)
del session
gc.collect()  # 强制销毁
```

**教训**：测试 `__del__` 必须：(1) 移除所有强引用 (2) `gc.collect()` (3) `capsys.readouterr()` 捕获 stderr。
